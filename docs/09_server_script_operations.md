# 服务端脚本操作规则

> 状态：可执行规范
> 范围：服务端构建、启动、停止、数据库初始化和开发清档
> 原则：先确认环境，再执行命令；生产数据不可用开发清档命令处理。

## 1. 命令总览

以下命令名是服务端脚本的操作约定。命令可由统一入口（例如
`deploy/tidesctl`）提供，也可由等价的 Windows/Linux 脚本提供；不同平台参数和路径以实际脚本为准。

| 命令 | 作用 | 是否运行服务端 | 是否修改业务数据 | 允许环境 |
|---|---|---:|---:|---|
| `build` | 编译服务端代码，生成或更新构建产物 | 否 | 否 | 开发、生产 |
| `start` | 启动已构建的服务端进程 | 是 | 仅写入运行时数据 | 开发、生产 |
| `stop` | 停止服务端进程，不删除数据和构建产物 | 否 | 否 | 开发、生产 |
| `init-db` | 创建数据库、表、索引并执行结构迁移 | 否 | 不得删除业务数据 | 开发、生产（受控） |
| `reset-dev` | 清空开发库中的全部业务数据，保留数据库结构 | 否 | 是，破坏性操作 | 仅开发 |

### 1.1 平台入口

统一入口 `tidesctl` 按平台提供以下脚本，命令名、参数和退出码语义保持一致：

| 入口 | 平台定位 | 使用规则 |
|---|---|---|
| `deploy/tidesctl.ps1` | Windows 主入口 | Windows 上开发、运维一律优先使用 PowerShell 调用；新功能和参数先在 `.ps1` 落地。 |
| `deploy/tidesctl.cmd` | cmd 兼容入口 | 仅用于无法使用 PowerShell 的旧环境和既有批处理集成；功能与 `.ps1` 对齐，`.ps1` 变更后同步。 |
| `deploy/tidesctl.sh` | Linux 入口 | Linux 开发机与生产/VPS 使用；行为与 Windows 入口等价。 |

- 三个入口的帮助（`help`、`--help`、`-h`）均以简体中文展示，遵循第 2 节规则；`reset-dev` 的破坏性警告必须在帮助输出中醒目出现，并写明“将清空全部业务数据且不可恢复、仅限开发环境、执行前需交互确认”。
- 旧 `deploy/tidesctl.bat` 视为遗留兼容脚本：冻结功能、不再扩展文档，保留期间不修改其行为以免破坏既有自动化；待 `.cmd` 兼容入口稳定后由后端 agent 按计划移除，移除前文档与测试继续按现状引用。

## 2. 帮助参数

统一入口必须提供以下等价的帮助用法：

| 用法 | 适用位置 | 规则 |
|---|---|---|
| `help` | 独立命令，或紧跟在命令名后 | 输出全部可用命令及其简要说明；例如 `tidesctl help`、`tidesctl build help`。 |
| `--help` | 独立选项，或放在命令名及其位置参数之后 | 输出当前入口或当前命令的帮助；例如 `tidesctl --help`、`tidesctl build --help`。 |
| `-h` | `--help` 的短选项别名 | 与同一位置的 `--help` 输出和退出状态完全一致；例如 `tidesctl -h`、`tidesctl build -h`。 |

- 帮助请求优先于实际操作参数处理；命令行同时包含帮助参数和其他参数时，只显示帮助，不执行目标命令。
- 帮助输出至少应包含命令格式、可用命令、可用选项、环境限制，以及 `reset-dev` 的破坏性警告；未知命令或选项应在错误提示中说明，并指引用户使用帮助命令。
- 帮助请求成功后以成功状态退出；不得因为当前服务未启动、数据库不可用、缺少数据库凭据或尚未构建而失败。
- `help`、`--help` 和 `-h` 只能用于查询操作，均不得启动或停止服务端、编译代码、连接或迁移数据库、写入业务数据、清空开发库、创建运行目录、修改配置或生成构建产物。
- 帮助输出不得包含密码、完整数据库连接串或其他敏感凭据；路径和配置示例使用非敏感占位符。

### 2.1 帮助文案原则

- 命令名、选项名统一使用英文小写（如 `build`、`start`、`reset-dev`、`--help`），不随界面语言变化；所有说明文字（命令用途、参数解释、环境限制、错误提示）使用简体中文。
- `reset-dev` 的帮助文案必须显示醒目的破坏性警告，明确写出“将清空全部业务数据且不可恢复、仅限开发环境”，并说明执行前需要交互确认；不得只写“重置开发数据”之类的模糊描述。
- 同一命令在 `help`、`--help`、`-h` 以及错误提示中引用的说明文案保持一致，避免同一命令出现多套描述。

### 2.2 Windows 脚本编码安全

- Windows 批处理脚本（`.bat`/`.cmd`）必须以 UTF-8 保存且不含 BOM，并在脚本开头使用 `chcp 65001 >nul` 切换控制台代码页后再输出中文，避免中文乱码或命令解析失败。
- 脚本中的命令名、路径和参数保持 ASCII；中文只出现在 `echo` 输出的说明文案中，不用于文件名、变量名或标签名。
- 帮助与警告文案中的中文不得使用控制字符或未转义的 `& | < > %` 等批处理特殊符号；百分号按批处理规则转义（`%%`）。
- PowerShell 脚本（`.ps1`）保存为 UTF-8 with BOM，保证 `powershell.exe`（5.1）正确识别中文；输出中文前不得假定终端编码，必要时显式设置 `[Console]::OutputEncoding`。
- `.cmd` 兼容入口沿用本节批处理编码安全规则；具体编码与换行约定以静态门禁验收标准为准，三入口帮助中文展示效果需一致。

## 3. 标准操作顺序

### 3.1 首次开发环境

```text
init-db -> build -> start
```

### 3.2 修改服务端代码后

```text
build -> start
```

如果服务端已有进程，先执行 `stop`，再执行 `build -> start`，避免继续运行旧构建产物。

### 3.3 开发数据需要从空库重新开始

```text
stop -> reset-dev -> init-db（仅当结构也需要迁移时）-> build -> start
```

`reset-dev` 不是重编译、不是重启、不是数据库迁移，也不是生产数据修复工具。

## 4. 各命令边界

### `build`

- 只编译服务端源码和必要的服务端资源，不启动进程、不连接生产数据库。
- 构建失败时不得执行后续 `start`；应保留失败信息并修复后重新构建。
- 构建产物属于运行文件，不等同于数据库结构或业务数据。

### `start`

- 只启动当前已确认构建成功的版本，并使用对应环境的外部配置。
- 启动前检查端口、运行目录、数据库连接配置和日志目录；已有实例运行时不得重复启动。
- 不得在 `start` 中隐式执行 `reset-dev`；`init-db` 也必须是显式步骤，不得静默清库。
- 生产启动应使用最小权限的服务账号，不使用 MySQL `root`。

### `stop`

- 只停止本项目服务端进程，并尽量使用优雅停止；不得通过模糊进程匹配杀死其他 Erlang/数据库进程。
- 不删除数据库、日志、构建产物或运行目录中的持久化数据。
- 生产停止前按发布或维护流程确认影响范围；停止后检查端口和健康检查，确认服务确已退出。

### `init-db`

- 只负责建库、建表、索引、约束和版本迁移；必须可重复执行或明确报告“已是最新结构”。
- 不得包含清空业务表、删除数据库、删除数据库卷或重置账号的逻辑。
- 生产执行前必须完成备份、变更审核和维护窗口确认；禁止把首次初始化与日常启动绑定。
- 数据库结构脚本、迁移记录和业务数据是不同概念，不能用 `reset-dev` 代替 `init-db`。

### `reset-dev`

- 仅允许连接明确标记为开发环境的数据库；脚本必须在执行前显示环境和目标库并要求确认。
- 清空账号、会话、房间、对局、结算、战绩、排行榜、统计、人机记录等全部业务数据。
- 保留数据库、表结构、索引、约束、迁移记录和脚本文件；不得删除仓库、静态资源或迁移脚本。
- 生产配置、生产域名、生产数据库连接或无法确认环境时，必须拒绝执行，而不是猜测。
- 该命令不得被 `start`、部署脚本、容器重启或自动恢复流程调用。

## 5. 开发/生产安全边界

### 开发环境

- 可以执行 `build`、`start`、`stop`、`init-db` 和 `reset-dev`。
- 执行 `reset-dev` 前必须停止服务端或确认没有写入中的事务，并核对目标库确为开发库。
- 开发清档应使用权限收敛的专用 MySQL 用户；`root` 仅用于必要的本地建库或权限维护。

### 生产环境

- 仅在发布或运维流程授权后执行 `build`、`start`、`stop`；`init-db` 只能作为经过审核的结构变更执行。
- 永久禁止执行 `reset-dev`，禁止通过删除数据库、容器卷或表来代替生产数据处理。
- 生产部署必须先备份并验证回滚方案；不能用开发配置、开发数据库或开发脚本覆盖生产配置。
- 服务端日常运行账号只授予实际所需的数据库权限，生产环境禁止使用 MySQL `root`。

## 6. MySQL 凭据规则

- 地址、端口、数据库名、用户名和密码必须在运行时由外部环境变量或不纳入版本控制的受保护本地配置注入。
- 真实凭据不得写入源码、配置样例、文档、测试数据、脚本、提交记录或容器镜像。
- 密码不得作为命令行参数或进程启动参数传递，避免出现在 shell 历史、进程列表和任务记录中。
- 日志、错误信息、审计记录和客户端响应不得输出密码或完整连接串；必要时只输出脱敏实例标识。
- 凭据文件必须限制本机访问权限并被版本控制忽略；示例文件只能使用变量名或占位符。

## 7. 执行前验收

- 已明确当前环境是开发还是生产。
- 已核对服务端代码版本、构建状态和目标数据库实例。
- `reset-dev` 已确认目标库为开发库，且操作者理解其会清空全部业务数据。
- 生产 `init-db` 已完成备份、审核和回滚准备。
- MySQL 凭据来自外部注入，命令行、日志和仓库中均没有明文密码。
