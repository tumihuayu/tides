# 账号系统与开发清档规则 v1.0

> 状态：已确认，可执行规范；账号、游客、教程、Bot、房间及正式统计身份边界已冻结  
> 范围：账号身份、游客身份、房间并发、历史数据处理、开发环境清档  
> 说明：本文是账号相关的当前唯一策划依据；与旧文档中的 `player_token` 方案冲突时，以本文为准。

## 1. 身份模型

### 1.0 冻结唯一口径

- `#role` 仅代表注册账号的长期数据身份。正式统计、账号资料和账号历史均以 `role_id` 归属；昵称、连接、设备、房间席位和 `player_id` 都不是长期身份。
- 账号登录成功后，服务端为该登录创建一个 `PlayerProcess`。`PlayerProcess` 是连接/在线运行实体，不是账号长期数据；它关闭或重建不改变 `role_id`。
- 游客没有 `#role`、没有 `role_id`、没有服务端会话或 `PlayerProcess`，只能在客户端运行纯客户端教程。游客刷新或断线后，教程从头重新开始。
- 游客完成教程后必须注册账号继续，或退出教程；游客不得借教程进入服务端大厅、房间或正式对局。
- Bot 是房间内的临时席位数据，没有 `#role`、`role_id`、账号档案或登录会话；房间关闭时 Bot 及其全部运行数据立即销毁。
- 房间结束后，仍有账号身份的玩家回到大厅。正式统计只接受带 `role_id` 的普通账号正式规则局；普通账号+Bot按既定规则统计，`practice`不统计，游客/Bot/教程不产生正式统计。

### 1.1 注册与登录

- 正式身份使用“账号名 + 密码”。账号名全局唯一，密码不得明文存储。
- 不提供找回密码、重置密码或人工找回流程。密码遗失时只能按开发环境或运营另行确认的账号处理流程处置，本期不设计找回功能。
- 一个账号对应一个身份。账号是跨设备、跨连接、跨房间校验的唯一业务身份，不因设备、浏览器或连接变化而生成新身份。
- 允许同一账号同时在多个设备登录。登录本身不互踢，不限制设备数量。

### 1.2 昵称

- 昵称是显示字段，账号名是登录字段；二者语义不同，后续可分别修改和展示。
- 首次注册或首次登录时，允许昵称先与账号名相同，不要求用户立即另设昵称。
- UI 在展示玩家时可显示昵称；需要展示登录身份或账号管理信息时显示账号名，不得把昵称当作账号唯一键。

### 1.3 游客

- 保留游客入口，但游客入口仅提供纯客户端教程，不创建服务端会话、`#role`、`role_id` 或 `PlayerProcess`。
- 游客刷新或断线后必须重新开始教程；不保存、不恢复服务端教程阶段，也不把游客教程状态迁移到账号。
- 教程完成后，游客只能选择注册账号继续，或退出教程；游客不能进入大厅、创建/加入房间或参加正式对局。

## 2. `player_token` 与历史数据

- 旧 `player_token` 只属于历史身份机制，不是新账号的登录凭证、账号主键或绑定依据。
- 旧 `player_token` 历史不迁移：不把 token 映射到账号，不合并战绩，不按昵称猜测归属，不提供自助认领。
- 账号系统上线时，旧 token 记录按开发清档规则清除；即使保留了静态代码或旧协议字段，也不能恢复旧 token 的身份关系。
- 新身份相关数据必须以 `role_id` 归属；允许多设备使用同一账号时，各登录分别创建 `PlayerProcess`，但读取同一账号长期数据。

## 3. 同账号单房间

- 同一账号同一时间最多属于一个房间。该限制是账号级限制，不是设备级限制。
- 同一账号在设备 A 已经位于房间时，设备 B 尝试入另一个房间，服务端必须拒绝该次入房并返回错误码 `already_in_room`。
- `already_in_room` 适用于创建后加入、直接加入和其他会使账号进入房间的入口；错误响应不得创建席位、改变房间人数或产生半成品会话。
- 设备 B 入同一房间也按同账号单房间处理，不新增第二个席位；客户端应展示“该账号已在房间中”的明确提示。
- 账号离开房间、房间解散或服务端确认连接失效后，才释放该账号的房间占用。断线宽限期内仍视为在房间中。
- 不做 IP、设备数量或设备指纹限制；“允许多设备登录”不等于“允许多房间占位”。

## 4. 数据库主库

- MySQL 是账号、密码凭证、账号资料、登录会话及账号与房间占用关系的唯一主库。
- 其他缓存、进程内状态或客户端存储只能作为临时数据或加速层，不能成为账号身份事实来源，也不能绕过 MySQL 的唯一性约束。
- 至少需要保证以下唯一性：账号名唯一；账号当前房间占用唯一。并发登录或并发入房时由服务端事务/约束保证结果一致。
- 密码使用带盐的强哈希存储；任何日志、接口响应和客户端持久化数据不得输出密码或密码明文。

### 4.1 本地 MySQL 凭据注入

- 本地开发所需的 MySQL 地址、端口、数据库名、用户名和密码必须在运行时从外部环境注入，或从不纳入版本控制的受保护本地配置读取；不得把真实凭据写入仓库中的源代码、配置文件、示例文件、文档、测试数据或脚本。
- 凭据不得作为命令行参数、命令行拼接字符串或进程启动参数传递，避免被 shell 历史、进程列表、任务记录或错误信息暴露；启动脚本应读取外部环境或受保护配置后直接建立连接。
- 凭据不得写入日志、异常堆栈、调试输出、连接失败信息、审计记录或客户端响应；日志中不得输出完整连接串，必要时仅允许输出已脱敏的实例标识。
- 受保护配置必须限制本机访问权限，并通过忽略规则或其他版本控制策略确保不被提交；示例配置只能包含变量名或占位符，不得包含可用密码。
- `root` 账号仅允许用于本地开发环境中的初始化、建库或权限维护等必要操作，不得用于生产环境，也不应作为服务端日常运行或清档的默认账号。
- 推荐为本地服务和清档分别使用权限收敛的专用 MySQL 用户，仅授予所需数据库和操作权限；专用用户凭据同样必须遵守本节的外部注入、受保护存储和不进日志规则。

## 5. 开发清档

### 5.1 入口与权限

- 清档只用于开发环境数据重置，由开发人员在启动脚本中通过一个明确的“一键清档”入口执行。
- 清档入口必须显式标注开发用途，并在执行前要求开发环境确认；生产启动流程不得默认调用、自动调用或暴露该入口。
- 清档不是迁移工具，不提供按账号、按表或按时间范围的选择性清理；执行即按本节范围清空全部数据库。

### 5.2 清理范围

一次开发清档必须清空 MySQL 中全部业务数据，包括但不限于：

- 账号、密码哈希、昵称、账号资料和登录会话；
- 账号与 `player_token` 的任何历史关系及旧 token 数据；
- 房间、房间成员、准备状态、座位、重连凭证和房间占用状态；
- 对局、牌局过程、结算、战绩、排行榜、统计和测试结果；
- 人机、机器人运行记录及其他业务配置数据（仅限存放在数据库中的部分）。

清档完成后，数据库应回到“无业务数据”的开发初始状态；必要的数据库表结构、索引、约束和版本迁移记录不属于业务数据，不得通过删除表结构代替清档。

### 5.3 不应清理的静态资源

清档不得删除、覆盖或重建以下不属于数据库业务数据的静态资源：

- `client/`、`server/`、`shared/`、`docs/`、`tests/` 中的源代码、协议、策划文档和测试脚本；
- 前端静态素材、图片、字体、音频、地图/卡牌定义等随版本发布的资源；
- 数据库迁移脚本、建表脚本、初始化结构定义和开发启动脚本本身；
- 依赖包、构建工具、运行时安装文件及版本控制元数据。

如果某项资源被错误存入数据库，应先调整存储设计；不能把删除静态资源作为清档的副作用。

## 6. 验收清单

1. 使用账号名和密码可注册、登录；账号名重复注册被拒绝；无找回密码入口。
2. 首次进入时可保留游客身份并运行纯客户端教程；游客无服务端会话，刷新/断线后从头开始。
3. 注册后昵称可先等于账号名；修改昵称不改变账号身份。
4. 同一账号可在两个设备同时登录，两个设备读取同一账号资料。
5. 设备 A 已在房间时，设备 B 尝试入任意房间返回 `already_in_room`，且不增加第二个席位。
6. 设备 A 离开或房间解散后，设备 B 才能成功入房；断线宽限期内仍返回 `already_in_room`。
7. 使用旧 `player_token` 或旧昵称登录/注册时，不会自动恢复或迁移旧历史。
8. 账号与房间占用数据以 MySQL 为唯一主库；并发入房不会产生双重占位。
9. 开发人员从启动脚本一键执行清档后，全部数据库业务表为空，旧 token、账号、房间、对局和统计均不存在。
10. 清档后源代码、文档、协议、测试脚本、静态素材、迁移脚本和数据库结构仍可正常使用。
11. 本地 MySQL 凭据来自外部环境或受保护配置，仓库中无真实凭据，命令行参数和进程参数中无密码，运行日志和错误输出中无密码或完整连接串。
12. `root` 仅用于本地开发的必要初始化或权限维护；服务端日常运行和清档使用权限收敛的专用用户，且专用用户权限满足实际操作范围。
