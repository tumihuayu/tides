## 1. 功能定位

对战结束后向全体在场真人玩家弹出结算弹窗（沿用 S6 遮罩形式扩展），一次性回答四个问题：① 我这局赢了还是输了；② 我最近状态如何（近七天胜率）；③ 我手热不热（连胜场次）；④ 这局具体结算了什么（名次/总分/明细/天梯变动）。

设计意图：给每局一个明确的情绪收束点（胜/负大字标题），并用「近 7 天胜率 + 连胜」制造短期目标感，服务 docs/06 的「轻量留存」定位。本期不做：结算分享、点赞/互动、奖励发放、赛季展示。

## 2. 冻结口径

### 2.1 胜负口径（①对战结果）

- **胜利：本人在 `game_over.scores` 中的 `rank = 1`。失败：`rank > 1`。**
- **并列第一**：多名玩家 `rank` 同为 1 时，**全员判胜**（与 docs/06 §4 wins「并列第1各计1胜」口径一致）。结算页不出现「平局」概念。
- 2 / 3 / 4 人局同一口径，不分局型。
- 人机（bot）与游客不展示胜负标题；bot 行无胜负语义。
- 秒退（rage_quit）被强制末名者，`rank > 1`，判负。
- 胜负判定在客户端按本人 rank 自判，服务端不新增 result 字段（见 §6 方案决策）。

### 2.2 近七天胜率口径（②）

- **窗口定义**：滚动时间窗，统计对局结束时间戳 `ts ≥ now − 7×24×3600 秒`（即 **604800 秒**）内的正式统计对局。边界**含**恰好 7×24h 整点（`≥` 取等）。不按自然日切分。
- **公式**：`近七天胜率 = wins_7d / games_7d`。
  - `games_7d`：窗口内正式统计对局数（与正式统计口径一致：**含普通账号+Bot 的正式规则局**，不含教程/practice/游客局/`stats_eligible=false` 局）。
  - `wins_7d`：窗口内 `rank = 1`（含并列第一）的对局数，与 wins 口径一致。
- **数据来源**：服务端档案维护独立的 7 日滑窗累计（带 ts 的历史或日桶），**不得从 `recent` 10 条推算**（7 日内可能超过 10 局，见分诊 §5 风险 1）。`recent` 保持 10 条上限不变。
- **展示精度**：整数百分比，四舍五入（如 `12/19 = 63%`）。同时展示样本数，格式：`63%（12胜/19场）`。
- **无对局（games_7d = 0，含新玩家）**：显示 `—`（不显示 0%、不显示 NaN），样本数行显示「近 7 天暂无对局」。
- **样本过少**：不做「样本不足」特别提示，如实展示百分比与样本数即可。

### 2.3 连胜口径（③）

- **字段**：档案维护 `win_streak`（当前连胜场数，整数 ≥ 0）。
- **更新规则**（仅在写入正式统计的对局结算时更新）：
  - 本局 `rank = 1`（**含并列第一**）→ `win_streak += 1`；
  - 本局 `rank > 1` → `win_streak = 0`。
- **秒退（rage_quit）**：强制末名即 `rank > 1`，按普通失败处理，**打断连胜**（清零）。
- **托管完成（auto_pilot 打完）**：按实际名次正常结算，胜则续连胜、负则清零，与正常对局无区别。
- **不计入统计的对局**（游客局、`stats_eligible=false`）：**不计入也不打断**——连胜数值原地保持不变。
- **连败不展示**：本期不维护/不展示连败场次；`win_streak = 0` 时显示「0 连胜」，不显示「连败 N」。
- 展示文案：`连胜 N 场`（N ≥ 2 时高亮，与 §4.2 一致）；N = 0 时显示「暂无连胜」。

### 2.4 本场结算信息清单（④）

结算页「本场结算」区展示以下内容，数据全部来自 `game_over.scores`（本人条目）与扩展后的 `my_stats`：

| # | 展示项 | 来源 | 格式/文案 |
|---|---|---|---|
| 1 | 本人名次 | scores 本人条目 `rank` | `#1` ~ `#4`，rank=1 加 👑 |
| 2 | 本人总分 | `total` | `38 分` |
| 3 | 计分明细 | `breakdown` | 逐项：订单/商站/货物/金币（沿用现有 SCORE_KEY_NAME 映射） |
| 4 | 天梯分变动 | `ladder_delta` | `+30`（涨潮青）/ `-10`（礁红）/ `0` / bot 与游客为 `—` |
| 5 | 结算后天梯分 | `my_stats.ladder`（本局已落盘后的当前分） | `天梯 1180` |
| 6 | 人机局标记 | `my_stats.recent[0].has_bot` 或当局房间成员含 bot | 行内小字标签「人机局」 |
| 7 | 托管标记 | 玩家 `auto_pilot=true` | 沿用现有「托管完成」标签 |
| 8 | 不计入标记 | `game_over.stats_eligible=false` | 见 §4.3 降级态 |

完整记分板（所有玩家的名次/总分/ladder_delta/breakdown）保留现有 S6 列表形式，按 total 降序排列。

## 3. 数据链路方案（冻结：方案 B）

采用分诊 §4.2 的**方案 B**，不改动 `game_over` 广播结构：

1. 服务端时序保证（现有实现已满足）：`tides_stats:record_game` 落盘**先于** `game_over` 广播。
2. 客户端收到 `game_over` 后：立即按本人 rank 渲染胜负标题与计分区（数据在 game_over 内），**同时发送 `get_my_stats`** 拉取扩展战绩。
3. `my_stats` 到达后填充统计区（近七天胜率 / 连胜 / 结算后天梯分）；到达前统计区为加载态。

**协议扩展提案（提请主协调同步 shared/protocol.md，v0.3 → v0.4）**：

`my_stats` 的 stats 增加三个字段：

```jsonc
{
  "win_streak": 3,      // 当前连胜场数，口径见 §2.3
  "games_7d": 19,       // 近 7×24h 滚动窗口内正式统计对局数，口径见 §2.2
  "wins_7d": 12         // 窗口内 rank=1（含并列）对局数
}
```

- 档案不存在（从未打正式局）时 `stats=null` 的行为不变。
- 胜率不由服务端下发，客户端按 `wins_7d/games_7d` 计算并格式化，避免精度口径双份维护。
- `game_over` 现有字段（scores/rank/ladder_delta/breakdown/room_mode/stats_eligible）**格式不变**，保证旧客户端兼容。

## 4. UI 布局规格

### 4.1 总体形式

沿用 S6 的全屏遮罩（`mask` + `mask-box`），升级为「战斗结算」弹窗，自上而下四区：

```
┌────────────────────────────────────────────┐
│ ① 标题区                                    │
│        胜  利        （大字，汐金 #D9A441）  │
│        失  利        （大字，雾白降饱和）    │
│     副标题：#1 · 38 分 · 天梯 +30           │
├────────────────────────────────────────────┤
│ ② 统计区（两格横排）                        │
│  近七天胜率          连胜场次               │
│  63%（12胜/19场）    连胜 3 场              │
├────────────────────────────────────────────┤
│ ③ 本场结算明细（全员计分板，沿用 S6 列表）  │
│  👑 玩家A   #1  +30   38分                 │
│     订单：20  商站：8  货物：5  金币：4     │
│  玩家B     #2  +10   31分  [人机·简单]     │
│  ...                                       │
├────────────────────────────────────────────┤
│ ④ 按钮区                                   │
│        [ 返回大厅 ]（主按钮）               │
└────────────────────────────────────────────┘
```

### 4.2 分区规格

**① 标题区**
- 大字标题二选一：「胜利」/「失败」，居中，字号显著大于其他内容（建议 32-40px），字距 0.1em。
- 颜色语义（遵循 05 §4.2，不另立含义）：胜利 = 汐金 `#D9A441` + 轻微发光；失败 = 雾白 `#E8E4D8` 降透明度（**不用礁红**，礁红仅用于损失数值；失败标题避免过强负面情绪）。
- 副标题一行：`#1 · 38 分 · 天梯 +30`（并列第一同样显示 `#1`）。
- 若 `stats_eligible=false`，标题区只显示「对局结束」，不显示胜负（无 rank 归属语义时兜底为失败态文案不允许——直接不显示胜负标题）。

**② 统计区**
- 两格等宽横排，窄屏（<560px）可纵排。
- 左格「近七天胜率」：大数字 `63%` + 小字 `12胜/19场`；无数据显示 `—` + 小字「近 7 天暂无对局」。
- 右格「连胜场次」：大数字 `连胜 3 场`；`win_streak=0` 显示「暂无连胜」；≥2 时数字用汐金高亮。
- 加载态：`get_my_stats` 未返回时两格显示占位 `…`（骨架/淡入），不得显示 NaN 或空白弹窗。
- 胜率数字颜色不作涨跌着色（中性主文字色），避免与获得/损失语义冲突。

**③ 本场结算明细**
- 完整保留现有 S6 计分板结构与交互：按 total 降序，每行名次 / 昵称 / bot·托管标签 / ladder_delta / 总分 / breakdown 逐项。
- 本人行高亮描边（汐金 1px）。
- 本人行下方追加一行小字：「结算后天梯 1180」（来自 `my_stats.ladder`，加载完成前不显示该行）。

**④ 按钮区**
- 主按钮一枚：「返回大厅」（沿用现有「再来一局」的实际行为 `backToLobby`——当前版本无匹配/续房系统，两者语义相同，统一命名为「返回大厅」）。
- 本期不加第二按钮；不阻断——`returned_to_lobby` 到达后**不得自动关闭结算弹窗**，由玩家主动点击关闭（见 §5.4）。

### 4.3 降级与异常态

| 场景 | 表现 |
|---|---|
| `stats_eligible=false`（不计入局） | 标题区显示「对局结束」（无胜负）；统计区整区替换为一行提示「本局不计入正式战绩」；明细区正常展示（ladder_delta 为 `—`） |
| 新玩家首战 | 胜负/明细正常；胜率格 `—` +「近 7 天暂无对局」（首战后 games_7d=1 则正常显示 `100%（1胜/1场）` 或 `0%（0胜/1场）`）；连胜按 §2.3 如实显示 |
| `my_stats` 返回 `stats=null` | 视同新玩家首战处理 |
| `my_stats` 加载失败/超时（>5s 未返回或收到 error） | 统计区显示「战绩统计加载失败」+ 一枚「重试」小按钮（重发 `get_my_stats`）；其余区域不受影响 |
| 结算弹窗打开期间断线 | 已渲染内容保留；统计区若仍在加载则转入加载失败态（含重试）；重连成功后由重连流程决定去向，弹窗不主动恢复 |

## 5. 边界与规则裁决

### 5.1 新玩家首战
无任何历史档案：胜率 `—`、连胜按本局结果（胜=「连胜 1 场」，负=「暂无连胜」）、明细正常。不出现 NaN/除零。

### 5.2 连败
不展示连败场次。连续失败期间连胜恒为「暂无连胜」，随后一胜即「连胜 1 场」。

### 5.3 断线与重连裁决
- **断线 30s 后由 AI 托管打完**：对局正常计入统计与 7 日胜率/连胜；若玩家未重连，其客户端看不到结算页属正常（数据已落盘，个人中心可查）。
- **game_over 阶段重连**：本期**不支持**重连恢复结算页。房间在 game_over 后 1s 解散并 `returned_to_lobby`；重连后玩家直接回大厅，可在个人中心查看战绩变化。不为此扩展 `reconnect` 协议。
- **秒退玩家**：判负、连胜清零；其客户端若仍在场则正常看到「失败」结算页。rage_quit 语义已扩展为「任意时刻主动退出，或断线 30s 内 grace 到期未归」，主动退出（leave_game）者已回大厅、看不到结算页属正常（数据已落盘）；细则见 `13_leave_game_rage_quit_v1.0.md`。

### 5.4 returned_to_lobby 与弹窗共存
`returned_to_lobby`（game_over 后约 1s 到达）**不得关闭或销毁结算弹窗**；客户端底层页面可切换到大厅，遮罩层保留至玩家点击「返回大厅」主动关闭。

### 5.5 不计入对局
游客、bot、`stats_eligible=false` 局不产生统计，**不打断连胜**；结算页按 §4.3 降级展示。

### 5.6 与个人中心（profile.ts）的关系
本期个人中心**不强制**新增连胜/7日胜率展示（字段已在 `my_stats` 中，前端可选展示）；若展示，口径必须与本文 §2 一致，不得另算。
