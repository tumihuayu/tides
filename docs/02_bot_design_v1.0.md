# 《潮汐商会》人机（AI Bot）功能策划案 v1.0

> 版本：v1.0 ｜ 状态：Bot 房间临时数据口径已冻结；旧统计/游客规则废止 ｜ 对应规则书：01_rulebook_v1.0.md、shared/protocol.md v0.1
> 本文只写设计意图与协议提案；`shared/protocol.md` 由主协调统一修改。

---

## 1. 功能定位

- **身份边界（冻结）**：Bot 只存在于房间运行态，没有 `#role`、`role_id`、账号档案或登录会话；房间关闭即销毁全部 Bot 数据，不落长期库。
- **统计边界（冻结）**：普通账号 + Bot 的正式规则局按既定规则统计；Bot 自身、游客、教程和 `practice` 均不产生正式统计。正式统计归属 `role_id`。

- **解决的问题**：凑不齐 2-4 名真人时无法开局；好友局缺 1-2 人时体验打折。人机用于「补位」，让任意 1 名真人即可开局。
- **人机可随时加入/被踢出**：仅在大厅（lobby）阶段，由房主操作添加或移除；游戏开始后人机名单锁定，不可增删。
- **真人中途掉线不接管**：本期**不做托管**。真人掉线仍走现有「超时自动弃置手牌第 1 张以 tide 打出」逻辑（protocol §牌局流程-4 / 规则书 FAQ-3）。人机是「从头到尾的虚拟玩家」，不是「真人替身」，两者行为边界清晰。
- **非目标（本期不做）**：难度分级、聊天/表情、托管接管、天梯/战绩系统。

## 2. 交互流程

### 2.1 大厅内操作

| 操作 | 权限 | 前置条件 | 结果 |
|---|---|---|---|
| 添加人机 | 仅房主 | 房间处于 lobby 且当前人数 < 4 | 服务端从名字池取一个未占用名字创建人机，自动置为「已准备」，广播 `room_update` |
| 移除人机 | 仅房主 | 目标玩家 is_bot=true 且房间处于 lobby | 人机从房间移除，名字归还名字池，广播 `room_update` |

- 可连续添加多个，直到满 4 人（1 真人 + 3 人机也合法）。
- **人机自动准备**：加入即 `ready=true`，不提供取消准备 UI；房主只需自己准备后即可 `start_game`。
- **人机不能当房主**：`host` 永远为 false；`create_room` 不接受人机身份（人机无连接、无 token）。
- **UI 表现**（供前端参考）：人机在大厅列表中名字后带「(人机)」徽标，无准备按钮；房主视角每个真人/人机条目旁有「移除」按钮（移除真人=踢人，若已有踢人功能则复用同一入口；本期仅要求移除人机）。

### 2.2 房主离开时的房主转移

房主在大厅离开时，按以下顺序裁决：

1. 剩余成员中有真人 → **座位顺序最靠前的真人**接任房主（host 转移），广播 `room_update`。
2. 剩余成员全是人机（或空无一人）→ **房间解散**，人机销毁，房间从 `list_rooms` 消失。
3. 人机永远不会成为房主，即使它是唯一剩余成员。

### 2.3 游戏中的人机

- 人机参与全部正常流程：发牌、提交、亮牌、结算、终局计分，与真人完全同规则、同信息量（服务端校验不区分人机/真人）。
- 人机不占用 WebSocket 连接；`connected` 恒为 true，不参与断线/重连逻辑。
- 游戏中真人掉线离开导致只剩人机时，房间照常运行到终局（人机互打），终局后房间按现有逻辑关闭；不做「只剩人机即中止」的特殊处理（本期简化）。

## 3. AI 行为设计（简单但拟人）

设计目标：**一个真人玩家打不过会懊恼、但不会觉得被算法羞辱**的对手。启发式 + 少量随机，不追求完美策略。

### 3.1 决策框架（select 阶段选 1 张牌 + 用途）

按优先级从上到下评估，命中即采用；每步附带随机扰动。

1. **能交订单就交**（权重最高）：
   - 手牌中有 deliver 卡，且货仓满足某张可见订单（公开或自己的隐藏）需求 → 出 deliver。
   - 潮汐加成倾向：当前为 rising 时优先交付；ebb 且有可交付的隐藏订单时优先交付。
2. **货满仓倾向卖货**：货仓 ≥3 件且手牌有 trade 卡 → 卖当前市价最高的货物；full 潮时卖货倾向 +30%。
3. **有明确买货机会**：某张可见订单只差 ≤2 件同种货物，且金币够买 → trade.buy 补货（low 潮买货倾向 +30%）。
4. **位置不对就航行**：当前港口既不能交付也不需要停留（例如订单限定了 port 而船不在那里），且金币 ≥ 航行费 → sail/tailwind 朝目标港移动；tailwind 优先于 sail（效率牌）。
5. **商站机会**：金币 ≥ 2 且当前港无自己商站、且该局尚未在任何港放满（粗略多数竞争判断：该港商站数 ≤2）→ post，倾向中后期（round ≥ 2）权重更高。
6. **兜底：留货或推潮**：
   - 手牌中有 cargo 面能补「订单缺口」的卡 → `mode=cargo` 留存（wild 声明为最紧缺货物）。
   - 否则 `mode=tide` 弃置：低潮纹卡优先弃（减少潮位扰动）；持「跟风/保守」人格时倾向弃潮纹 0-1 的卡。
7. **扰动**：每步命中后有 15% 概率跳过该选项继续向下评估；最终兜底永远是合法的（tide 弃牌恒合法），保证不会卡死。服务端仍需对 AI 提交做与真人完全相同的校验，非法提交回退为「弃手牌第 1 张 tide」（复用 auto_submit 逻辑）。

### 3.2 人格倾向（跟风/保守）

每台人机开局随机抽 1 个人格，整局不变，影响潮汐弃牌与交易倾向：

| 人格 | 抽中概率 | 行为倾向 |
|---|---|---|
| 稳健 | 40% | 默认权重，无明显偏向 |
| 跟风 | 30% | 弃牌推潮时倾向与上回合多数派同向（潮纹高的卡更愿意打出），交易倾向跟随当前最高价货物 |
| 保守 | 30% | 从不主动推潮（优先弃潮纹 0 卡），金币 <4 时不买货不设站 |

人格不进协议、不对真人暴露（隐藏信息，增加拟人感）。

### 3.3 思考延迟

- 每个 select 阶段开始后，人机延迟 **1-3 秒均匀随机** 再提交，模拟真人读牌节奏。
- 同一回合多台人机的延迟各自独立随机（避免同帧齐提交穿帮）。
- 实现建议（供后端参考）：room 进程在 `phase_changed(select)` 时为每台人机 `erlang:send_after(rand 1000-3000ms)` 调度一次决策消息；若回合因真人全部提交而提前结束，取消未到期的定时器。超时保护：若人机因任何原因未提交，沿用现有 45s 超时 auto_submit 兜底。

### 3.4 人机命名池（20 个，中文商人风）

潮生、白汐、阿橹、石翁、雾婆、江算子、秦半两、苏锦娘、戚灯芯、洛满仓、韩听涛、岑拾贝、伍短衫、贺兰舟、鲍三盐、邬见礁、穆摇橹、童小汛、甘回澜、岳镇潮

- 服务端为每个房间维护「本房已用名」集合，添加人机时从池中随机取未占用者；移除后归还。
- 若未来允许同一玩家开多房，名字池按房间隔离即可，无需全局唯一。
- 大厅展示为「名字 + (人机)」后缀，后缀由前端依据 `is_bot` 字段渲染，不写入 name 本体。

## 4. 协议变更提案（供主协调修改 shared/protocol.md）

> 以下均为草案，字段名遵循现有 snake_case 风格；`reason`/`code` 一律字符串。

### 4.1 新增客户端→服务端消息

| type | payload | 说明 |
|---|---|---|
| `add_bot` | `{}` | 仅房主、仅 lobby、房间未满（<4）。成功广播 `room_update`；失败回 `error` |
| `remove_bot` | `{player_id}` | 仅房主、仅 lobby、目标须 is_bot=true。成功广播 `room_update`；失败回 `error` |

JSON 示例：
```json
{"type":"add_bot","room_id":"A7Q2","player_id":"p1","action_id":"f47ac10b","seq":7,"ts":1730000100,"payload":{}}
```
```json
{"type":"remove_bot","room_id":"A7Q2","player_id":"p1","action_id":"9b2f31c2","seq":8,"ts":1730000110,"payload":{"player_id":"bot_2"}}
```

错误码（字符串）建议：`not_host`、`not_in_lobby`、`room_full`、`not_a_bot`、`player_not_found`。

### 4.2 `PlayerBrief` 增加 `is_bot` 字段

现状：`{id, name, ready, host, connected}`
提案：`{id, name, ready, host, connected, is_bot}`

```json
{"id":"bot_2","name":"洛满仓","ready":true,"host":false,"connected":true,"is_bot":true}
```

- 影响 `room_update`（大厅）消息中的 `players[]`。
- 建议 `game_started`/`state_sync` 的 `public_state.players[]` 同样补 `is_bot`（前端头像/徽标需要），示例：
```json
{"id":"bot_2","name":"洛满仓","coins":3,"vp":0,"cargo_count":0,"submitted":true,"connected":true,"is_bot":true}
```

### 4.3 人机 ID 与约束

- 人机 player_id 建议格式 `bot_1`、`bot_2`…（房间自增），与真人 `p1` 风格区分且可排序；真人重连 token 不适用于人机（人机无 token，`reconnect` 拒绝 bot id）。
- `start_game` 人数校验不变：含人机总数 2-4；「全员已准备」判定中 `is_bot=true` 的玩家视为恒已准备。
- 房主转移规则写入协议「断线」或新增「房主转移」小节：房主离开/断线超过宽限期后，房主按座位顺序转移给下一位 `is_bot=false` 且 `connected=true` 的玩家；无真人则解散房间。
- 无需新增服务端→客户端消息类型；人机行动通过现有 `reveal_cards`/`state_sync`/`action_log` 自然呈现。

### 4.4 不变更项（明确范围）

- 不新增「托管」消息（takeover/assume_bot 等），本期协议不含。
- 不新增聊天消息。
- 人机不在 `room_list` 中单独标注（`player_count` 含人机即可，外部观感与满员房一致）。

## 5. 数值与体验边界

| 项 | 规则 |
|---|---|
| 开局人数 | 总人数（真人+人机）2-4 人；真人最少 1 人。即「1 真人 + 1-3 人机」可开局，「0 真人」房间不存在（房主必是真人） |
| 天梯/战绩 | 普通账号 + Bot 正式规则局按既定规则计入，归属账号 `role_id`；Bot、游客、教程和 `practice` 不计入 |
| 结算与奖励 | 人机正常参与局内计分与排名（局内体验需要），但终局结果不落库到人机名下 |
| 超时 | 人机决策 1-3s 内必提交；45s 超时兜底逻辑对人机同样生效（防御性） |
| 信息量 | 人机只使用公开信息 + 自己的私有信息（手牌/货仓/隐藏订单），不读取他人手牌、牌库顺序——与真人信息边界完全一致 |
| 并发上限 | 单房间人机 ≤3；全服人机总数不做本期硬限（房间内调度，开销极小），性能问题留待后端压测 |

## 6. 后续版本展望

1. **难度分级**：新手（提高随机扰动至 30%）/ 标准（本方案）/ 老练（前瞻 1 回合潮汐落点、针对商站多数做博弈）；`add_bot` 增加 `{difficulty}` 参数。
2. **托管接管**：真人掉线超过宽限期后由人机代打（沿用同一决策模块），真人重连后交还控制权；需要新增 `takeover` 相关协议与 UI。
3. **人机聊天与表情**：预置短句池（开局问候、被压价时吐槽、终局客套），以固定概率 + 事件触发发送，需要新增 `chat` 消息类型。
4. **人格可视化**：赛后结算页展示人机人格标签（「本局的洛满仓是个保守派」），增强记忆点。
5. **练习模式**：单机离线人机局（协议不变，服务端允许无网开局或本地模拟）。

## 附：验收清单（供测试PM）

1. 1 真人创建房间 → 添加 1/2/3 台人机 → 可开局；人数 <2 时 `start_game` 被拒绝。
2. 人机加入即 ready；`room_update` 中 `is_bot=true`、`host=false`。
3. 房主离开后：有真人则真人接任房主；只剩人机则房间解散。
4. `remove_bot` 对人机生效、对真人返回 `not_a_bot`；非房主调用返回 `not_host`。
5. 整局（含人机）冒烟：人机在 1-3s 内提交，12 回合正常打完，`game_over` 正常下发，无任何 `action_rejected` 由人机触发（非法提交应被 AI 内部兜底消化）。
6. 人机名字池 20 个不重复，移除后名字可再被取走。

## 7. 废止旧规则

- 废止本文件原“含人机对局不计入任何持久化战绩”的描述；正式 Bot 局以 `role_id` 归属普通账号并按既定规则统计。
- 废止任何为 Bot 创建长期账号、`#role`、`role_id` 或独立战绩档案的方案。
